# Third Swarm ($SWARMLER) logo options

All five PNGs are **1024 × 1024**, opaque, 8-bit RGB. The shared palette is olive green, near-black, coral pink, warm cream and brown, retaining the creator reference's frog, swept hair and expressive mouth in a new cartoon treatment.

1. [logo-1.png](logo-1.png) — **Mascot:** a confident frog with a swept quiff, brown scarf and thumbs-up; drawn with built-in image generation.
2. [logo-2.png](logo-2.png) — **Minimal icon / selected wallet logo:** one broad frog face, large eyes and coral smile on a full-bleed brown background; drawn with built-in image generation.
3. [logo-3.png](logo-3.png) — **Lettermark:** custom block paths spell **SWAR / MLER**, with frog eyes, swept hair and a coral smile; drawn with code in [logo-3.svg](logo-3.svg) and rendered with FFmpeg's librsvg decoder after image generation rejected this request.
4. [logo-4.png](logo-4.png) — **Minted emblem:** bronze relief and green enamel frog on a dark background; drawn with built-in image generation.
5. [logo-5.png](logo-5.png) — **Illustrative meme:** a laughing, wide-eyed frog against broad coral and cream comic rays; drawn with built-in image generation.

The selected [artifacts/logo.png](../artifacts/logo.png) is an exact copy of option 2. Its artwork was generated by the built-in image tool, not drawn with code. It has no text, numerals, enclosing frame, or transparent margins. The brown background fills the square. Only option 3 contains lettering, and that lettering is the ticker.

The [creator's supplied reference](https://fxumiqjngmabtgvruvka.supabase.co/storage/v1/object/public/forum-attachments/posts/mv1jblgp-o6my9g.png) informed the subject and colors. The character illustrations use a simple scarf and no insignia. Options 4 and 5 used the newly generated option 1 as their reference to keep the collection consistent.

**Draft count:** four image-generated drafts and one code-drawn draft were completed, one per delivered option. All five were retained; no rendered drafts were discarded. One additional image-generation request for the lettermark was rejected by the tool before an image was produced, so the explicitly permitted SVG fallback was used. No other retry or redraw was needed.

**Selection:** option 2 was chosen for the wallet because its single face has the strongest small-size silhouette. Option 1 has extra hand/scarf details; option 3 contains text; option 4 has a coin rim; option 5 has a more detailed expression and background. Those are intentional features of their requested approaches, but they make them less suitable for the stricter 32-pixel wallet criterion.

The generated originals arrived at 1254 × 1254. FFmpeg resampled them to the required 1024 × 1024 using Lanczos; this was only size normalization, not a redraw or compositing of the artwork. The fallback SVG was rendered directly at 1024 × 1024:

```sh
ffmpeg -hide_banner -loglevel error -i logos/logo-3.svg \
  -vf format=rgb24 -frames:v 1 -y logos/logo-3.png
```

**Visual review:** every delivered image was inspected, including actual-size 64-pixel square and circular thumbnails on light and dark backgrounds. The selected icon was also inspected as an actual-size 32-pixel circle on both backgrounds. The eye shapes, black hair and coral mouth remain distinct. Review sheets: [64 px](../artifacts/size-check-64px.png), [32 px](../artifacts/wallet-check-32px.png).

**Offline checks:** run `forge build --offline`, `forge test --offline` and `python3 logos/verify.py` from the repository root. The Foundry suite checks the five deliverable files, their opaque 1024-square PNG structure and reviewed SHA-256 fingerprints, that all five options differ, and that `artifacts/logo.png` exactly equals option 2. It includes rejection tests and 2,000 fuzz cases for incorrect dimensions. The Python standard-library check additionally validates every chunk CRC and decompresses the image data. No downloaded dependencies are needed. All six PNG files must be included in the submission commit; filesystem read permissions are limited to those exact paths. Git metadata is read-only on this worker, so committing must be completed by the submitting worker as explained in the root README.

This bounded assignment supplies artwork and artifact validation. It does not implement, test, deploy or attest the launch's token or Uniswap hook.
